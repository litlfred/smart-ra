comment
This comment lists, in one place, every location the Ministry has identified where the guidance treats the persistence of clinical data or the information-model layer, so that the individual comments that follow are read as a set rather than separately. We have set them out this way because a reader encountering these passages in isolation will reasonably draw different conclusions from each, which is the opposite of what guidance of this kind is for. WHERE THE GUIDANCE ALREADY ACCEPTS AN OPEN INFORMATION-MODEL FORMALISM FOR CLINICAL DATA 1. Annex D.1, page 230, lines 36–37 — EHRbase is listed under Lifelong Health Record as "an open-source, openEHR-conformant clinical data repository that stores and queries health data against openEHR archetypes and templates", alongside HAPI FHIR Server at page 229 lines 33–35. 2. Appendix C, page 175, functional requirement 2, status REQUIRED — the LIMR "shall support the representation of models conforming to recognised health data standards, including … openEHR archetypes and templates". 3. Appendix C, page 174, lines 81–85 — multi-formalism support is a core attribute; a national LIMR "should bridge between them rather than mandate one". 4. Appendix C, page 172, architecture placement box — the LIMR "is anchored in internationally recognised standards including HL7 FHIR StructureDefinitions, openEHR archetypes, and WHO SMART Guidelines data dictionaries". 5. Appendix C, page 156, line 43 — ISO 18308:2011 is cited as characterising an EHR architecture. WHERE THE GUIDANCE NAMES ONLY FHIR, OR PRESCRIBES IT FOR PERSISTENCE 6. Section 2.2.2, page 28, lines 148–151 — the Open Standards enabling condition names HL7 FHIR, ICD, LOINC and SNOMED CT. No information-model formalism. 7. Figure 2.2, page 30 — the full-STAC "S" grouping lists HL7 FHIR, ICD, SNOMED CT, LOINC, CQL. No information-model formalism. 8. Section 2.3, principle II, page 32, lines 233–234 — "The architecture points to FHIR-based approaches as the direction of travel." 9. Figure 3.2, page 48, Shared Data Layer — the Lifelong Health Record element is annotated "FHIR-based store". It is the only element in the figure carrying a storage technology. 10. Figure 3.5, page 66 — the same Shared Data Layer is repeated with the identical "FHIR-based store" annotation. 11. Figures 3.2 and 3.5 — the Logical Info Model Repo element lists its artefacts as "FHIR profiles · eObjects · IPS · datasets". openEHR archetypes and templates are absent, contrary to item 2 above. 12. Figures 3.2 and 3.5, Interoperability column — openEHR is listed under "Open standards — Exchange & content". It is an information-model formalism, not an exchange standard. 13. Section 3.6.2, page 74, lines 811–820 — the paragraph naming the standards the architecture references lists nine, across exchange, terminology, identifiers, imaging and content. None for structure, although lines 805–807 state that the LIMR governs structure. WHERE THE INFORMATION-MODEL COMPONENT IS OMITTED OR DEFERRED 14. Section 2.2.1, page 28, capability table — the LIMR is asterisked as "an enabler that can be built up as maturity grows, rather than part of the minimum foundation". 15. Appendix C, page 172, architecture placement box — "Countries should approach the LIMR as a progressive enabler, not an immediate prerequisite." 16. Figure 3.4, page 51 — the Metadata Components group lists the four registries and the Terminology Service; the LIMR is absent. 17. Appendix E, Goal 1, page 236, lines 238–240 — the foundational component list omits the LIMR. WHERE THE GUIDANCE ARGUES THE MINISTRY'S CASE ITSELF 18. Section 3.6.2, page 74, lines 822–830 — "Standards designed primarily for data in motion are highly extensible, and uncoordinated extension produces what are sometimes described as interoperable silos." 19. Section 4.3.3, page 96, lines 319–321 — "A FHIR profile is a representation of that logical model, not a replacement for it." 20. Appendix C, page 173, lines 35–42 — two systems can exchange in HL7 FHIR "and still fail to interoperate meaningfully". 21. Appendix C, page 157, lines 107–110 — the LHR core attribute requires "storage of health data in accordance with the logical information structures published through the LIMR". 22. Section 2.3, principle VIII, page 35, lines 381–389 — the architecture should deliver "clear separation between the data a country owns and the systems that process it", with no mechanism named. Items 6 to 17 are inconsistent with items 1 to 5 and with items 18 to 22. The Ministry's recommendation is that items 6 to 13 be amended to name an open information-model formalism for persisted clinical data alongside HL7 FHIR, and that items 14 to 17 be amended so that a governed minimum information model is treated as foundational.
